# PostgreSQL setup (not a production cutover)

Flyway alone owns migrations. `migration/V1__*.sql` through `V15__*.sql` are
PostgreSQL translations of `backend/src/main/resources/db/migration`, the immutable
MySQL history. Do not edit that history or copy its Flyway schema-history table into
PostgreSQL. Do not combine both migration directories: they use the same versions.
No Node startup migration runner or Prisma migration system is introduced.

## Local setup — commands for the operator, not executed by this change

Prerequisites: a PostgreSQL server you have installed and started yourself,
PostgreSQL client tools, and a Flyway CLI distribution supporting PostgreSQL.
Run the following against a NEW local database only. No AWS changes are needed.
The `-P` option prompts for the new role password; do not put real credentials in Git.

```bash
createuser --host=127.0.0.1 --username=postgres --pwprompt sarakusetu_local
createdb --host=127.0.0.1 --username=postgres --owner=sarakusetu_local sarakusetu_pg
psql --host=127.0.0.1 --username=postgres --dbname=postgres \
  --command="ALTER DATABASE sarakusetu_pg SET timezone TO 'UTC'"

cd backend-node
export FLYWAY_URL='jdbc:postgresql://127.0.0.1:5432/sarakusetu_pg'
export FLYWAY_USER='sarakusetu_local'
# Supply FLYWAY_PASSWORD securely through your environment; never commit it.
flyway -configFiles=db/postgresql/flyway.conf info
flyway -configFiles=db/postgresql/flyway.conf validate
flyway -configFiles=db/postgresql/flyway.conf migrate
flyway -configFiles=db/postgresql/flyway.conf validate
```

`migrate` above is a Flyway command for you to run after reviewing the target.
Never run `prisma migrate`, `prisma db push`, or any reset command.
V4 inserts the three original chocolate products, including their original URLs.
The optional `scripts/seed-catalog.ts` is a separate data-writing utility, not a
migration, and has not been run. Do not run it automatically during setup.

Set DATABASE_URL in your local environment to the PostgreSQL URL shown in
`.env.example`, with actual URL-encoded credentials. The existing `.env` was not
changed and may still contain a MySQL URL. Then, from backend-node:

```bash
npx prisma validate --schema prisma/schema.prisma
npx prisma generate --schema prisma/schema.prisma
npm run lint
npm run build
npm test
```

Validate/generate do not connect to or modify a database. Generation does replace
the local generated `@prisma/client`; the default is now PostgreSQL. Install/build
procedures must generate the client before starting this backend.

## Tests and verification limits

Normal tests need no database. They check all 15 source checksums, unchanged V4,
identity columns, named constraints/indexes, generated model/column mappings and
client construction. Existing route/service tests exercise query shapes with mocks.
These checks do NOT prove SQL execution or a real PostgreSQL connection works.

An opt-in read-only smoke test uses `POSTGRES_TEST_DATABASE_URL`, never the runtime
DATABASE_URL. It rejects non-loopback hosts and any database name other than
`sarakusetu_test`. It does not create tables, seed, or start a server. To run it,
create a separate local test database and apply the same Flyway migrations first:

```bash
createdb --host=127.0.0.1 --username=postgres --owner=sarakusetu_local sarakusetu_test
FLYWAY_URL='jdbc:postgresql://127.0.0.1:5432/sarakusetu_test' \
  flyway -configFiles=db/postgresql/flyway.conf migrate
# Set POSTGRES_TEST_DATABASE_URL securely to this local test database's Prisma URL.
npm test -- src/database/postgresql.test.ts
```

The smoke test connects with the generated client, starts a read-only transaction,
and reads all 14 models plus the cart/order/auth/inventory/payment relationships.
It deliberately does not exercise writes against an existing database. A separate
approved disposable-database integration run is still needed before production cutover.

## Translation and breaking differences

- `BIGINT AUTO_INCREMENT` becomes `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
  Explicit IDs can be imported, but sequences must subsequently be advanced past
  imported maxima by an operator; explicit inserts do not advance the sequence.
- `INT` becomes `INTEGER`. `stock_quantity INT UNSIGNED` becomes `INTEGER` with
  `ck_wholesaler_inventory_stock_nonnegative CHECK (stock_quantity >= 0)`.
  Maximum stock falls from 4,294,967,295 to 2,147,483,647. Audit existing data before
  importing; do not silently truncate. The check is maintained in SQL, not Prisma.
- Inline `INDEX`/`KEY` becomes separately named `CREATE INDEX`; `UNIQUE KEY`
  becomes a named UNIQUE constraint. All explicitly named historical indexes,
  constraints and foreign keys are retained. PostgreSQL-generated primary-key
  index names differ from MySQL's `PRIMARY`.
- `AFTER customer_id` is removed. Column names and relationships are unchanged;
  consumers must use column names rather than physical column order.
- `TIMESTAMP(6)` stays microsecond-precision timestamp WITHOUT time zone, matching
  Prisma `@db.Timestamp(6)`. Unlike MySQL TIMESTAMP, it does not perform timezone
  conversion. Export MySQL timestamps in UTC and use UTC PostgreSQL sessions.
  JavaScript Date still has millisecond precision. CURRENT_TIMESTAMP in PostgreSQL
  is transaction-start time, which can differ from MySQL statement-time behavior.
- Decimal precision/scale, lengths, nullability, defaults and Boolean declarations
  are preserved. PostgreSQL Boolean accepts true/false, not arbitrary MySQL tinyint
  values; check old data. NULL values remain distinct in nullable unique constraints.
- Text comparison/uniqueness/sorting follows PostgreSQL collation and can differ
  from MySQL case-insensitive collations. No speculative collation is imposed.
- SQL foreign keys retain default NO ACTION behavior (nondeferrable); Prisma
  explicitly declares NoAction on delete/update, avoiding its nullable-relation
  SetNull and update Cascade defaults, which were not present in Flyway SQL.
- PostgreSQL aborts a transaction after an SQL error. The cart's unique-race retry
  already retries outside the failed transaction. Concurrent workflows and default
  isolation differences still require database integration/load testing.

These scripts create a fresh schema, NOT a MySQL data-copy pipeline. Importing
existing rows, reconciling V4 seed IDs, sequence reseeding, collation/UTC checks,
backups, traffic cutover and rollback are separate operator-controlled work.
Do not point the old Spring application at this database: its configuration and
MySQL migrations remain unchanged.

## Preserved MySQL client mapping

`prisma/schema.mysql.prisma` is a byte-for-byte copy of the previous mapping.
To keep using MySQL in a separate checkout/build, supply the existing MySQL URL
and explicitly generate that client:

```bash
npx prisma validate --schema prisma/schema.mysql.prisma
npx prisma generate --schema prisma/schema.mysql.prisma
```

Both mappings intentionally generate the same `@prisma/client` import used by the
application. They cannot be active simultaneously in one node_modules directory.
Re-generate with `schema.prisma` to return to PostgreSQL. The PostgreSQL mapping tests
expect the PostgreSQL-generated client. No database is altered by either generation.
